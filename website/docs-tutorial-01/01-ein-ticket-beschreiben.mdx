# AB 01 – Ein Ticket beschreiben

*Dauer: etwa eine Doppelstunde.*

## Die Situation

> Bei der **HiTec GmbH** melden sich Mitarbeitende beim Support, wenn etwas nicht funktioniert: Der Drucker druckt nicht, das VPN geht nicht, ein Passwort ist vergessen. Jede solche Meldung ist ein **Support-Ticket**.
>
> So läuft das bisher:
>
> 1. Frau Albers aus dem Büro 2 ruft beim Support an: „Der Drucker druckt nicht.“
> 2. Jonas Beck vom Support trägt eine neue Zeile in die Excel-Datei `Tickets.xlsx` auf dem Netzlaufwerk ein. Die Nummer vergibt er von Hand.
> 3. Er schätzt die Dringlichkeit und trägt eine Priorität ein.
> 4. Wenn sich jemand um das Ticket kümmert, schreibt er den Namen dazu. Ändert sich etwas, überschreibt er die Zelle.
>
> | Nr | Titel | Status | Priorität | Bearbeiter |
> |---|---|---|---|---|
> | 3 | Drucker im Büro 2 druckt nicht | offen | 2 | |
> | 7 | Software-Lizenz läuft ab | in arbeit | hoch | Jonas Beck |
> | 8 | WLAN im Besprechungsraum instabil | Erledigt | 2 | Mara Voss |
>
> Mit der Zeit gibt es Ärger. In der Tabelle steht mal „in Arbeit“, mal „in arbeit“, mal „Erledigt“. Die Priorität ist mal eine Zahl, mal das Wort „hoch“, und die Auswertung zählt falsch. Zwei Kollegen öffnen die Datei gleichzeitig, und einer überschreibt die Änderung des anderen. Bei Ticket 5 fehlt die Nummer.
>
> Deshalb entsteht eine **Weboberfläche** für die Tickets. Dahinter braucht die Software für jedes Ticket eine **feste Form**, die solche Fehler gar nicht erst zulässt.
>
> **Dein Auftrag:** Beschreibe ein Ticket in TypeScript so genau, dass der **Compiler** Fehler findet, bevor sie jemand bemerkt. Dazu schreibst du die ersten drei kleinen Funktionen.

## Lernziele

Nach Bearbeitung dieses Arbeitsblatts kannst du:

- die Ausgabe von **Compiler** und **Tests** lesen und beide unterscheiden
- erklären, warum ein Programm trotz **Typfehlern** läuft
- Daten mit einem **Interface** beschreiben, mit optionalen und schreibgeschützten Feldern
- mit einem **Union-Typ** festlegen, welche Werte erlaubt sind
- einen **Template-String** und den Operator `??` einsetzen

## So arbeitest du

In diesem Tutorial hast du zwei Prüfer, die dir Rückmeldung geben. Sie prüfen Verschiedenes:

| Prüfer | Befehl | Er sagt dir |
|---|---|---|
| **Compiler** | `npm run check` | ob die **Typen** zusammenpassen |
| **Tests** | `npm run test:ab01` | ob dein Code das **Richtige tut** (nur die Tests dieses Arbeitsblatts) |
| beide | `npm run verify` | beides nacheinander, mit Zusammenfassung. Ganz grün wird es erst nach AB 03, weil die Tests der späteren Arbeitsblätter bis dahin rot sind. |

### Aufgabe 3 – Das Ticket beschreiben

*Etwa 20 Minuten.*

Ein Ticket besteht aus diesen Feldern:

| Feld | Bedeutung | Beispiel | Pflicht? |
|---|---|---|---|
| `id` | Nummer des Tickets, ändert sich nie | `7` | ja, **nur lesbar** |
| `title` | Kurzbeschreibung | `'Drucker defekt'` | ja |
| `status` | Bearbeitungsstand | `'offen'` | ja |
| `priority` | 1 = hoch, 2 = mittel, 3 = niedrig | `1` | ja |
| `assignee` | Wer sich kümmert, kann noch niemand sein | `'Mara Voss'` | **nein** |
| `createdAt` | Datum der Meldung | `'2026-11-02'` | ja |

<Task id="ts-ab01-a3-open">Öffne `src/ticket.ts`. Dort steht als Platzhalter `export type Ticket = any;` (was `any` bedeutet, erfährst du gleich unter dem Gerüst). Ersetze die Zeile durch ein **Interface**, das die Form eines Tickets beschreibt, und ergänze die vier fehlenden Felder. Vorerst ist `status` ein Text (`string`) und `priority` eine Zahl (`number`). `assignee` und `createdAt` sind ebenfalls Texte, auch das Datum (Begründung unten). Der Block unten ersetzt die alte Zeile **ganz**, lösche sie also.</Task>

:::info Meldet der Compiler „Duplicate …“?
Dann steht derselbe Name zweimal in der Datei, zum Beispiel `Duplicate identifier 'Ticket'` oder `Duplicate function implementation`. Du hast die alte Version nicht gelöscht. Entferne sie: Was im Block steht, ersetzt sie **vollständig**. Das gilt in diesem Arbeitsblatt für jeden Block, der eine ganze Funktion oder ein ganzes Interface zeigt.
:::

```ts title="src/ticket.ts"
export interface Ticket {
  readonly id: number;
  title: string;
  // Ergänze: status, priority, assignee (optional!) und createdAt
}
```

<details>
<summary>Tipp: Wie macht man ein Feld optional?</summary>

Mit einem Fragezeichen hinter dem Namen: `assignee?: string;`. Dann darf das Feld fehlen. Liest du es trotzdem, ist sein Wert `undefined`. Der Compiler erinnert dich später daran, diesen Fall zu behandeln.

</details>

**Was war das `any`?** Mit `type Name = …` gibst du einem Typ einen Namen. Der Starter hatte `Ticket` vorerst mit `any` belegt: Ein Wert vom Typ `any` darf alles sein, und der Compiler prüft **nichts** daran. Mit `any` hättest du `ticket.titel` oder `ticket.id = 'abc'` schreiben können, und es hätte keine Meldung gegeben. Deshalb übersetzte das Projekt am Anfang fehlerfrei, obwohl noch kein Typ beschrieben war.

Das erklärt auch die Meldungen `Unused '@ts-expect-error' directive` aus Aufgabe 1: Die Prüfungen in `src/types.check.ts` erwarten Fehler, aber mit `any` verbietet der Compiler nichts. Du ersetzt Platzhalter für Platzhalter durch echte Typen, und die Meldungen verschwinden nach und nach. In deinen eigenen Programmen solltest du `any` möglichst nie schreiben, weil es genau die Prüfung abschaltet, wegen der es TypeScript gibt. Mehr dazu steht im Infoblatt [Typen: Daten beschreiben](/infoblaetter/typen).

**Warum ein Interface und keine Klasse?** In Java hättest du für das Ticket eine Klasse geschrieben, mit Feldern, Konstruktor, Gettern und Settern, und Tickets mit `new Ticket(...)` erzeugt. In TypeScript gehst du bei Daten oft einen einfacheren Weg: Ein Ticket ist ein gewöhnliches Objekt, das du direkt hinschreibst oder als JSON vom Server bekommst:

```ts
const ticket = { id: 7, title: 'Drucker defekt', status: 'offen' };
```

Ein `interface` legt nur fest, **welche Felder** so ein Objekt haben muss und welche Typen sie haben. Es ist keine Vorlage, aus der man Objekte erzeugt: Es hat keinen Konstruktor, du benutzt kein `new`, und nach dem Kompilieren ist es verschwunden. Der Compiler prüft damit nur, ob ein Objekt passt.

| Java | TypeScript |
|---|---|
| `class Ticket` mit Feldern, Konstruktor und Gettern | `interface Ticket` nur mit den Feldern |
| `new Ticket(7, "Drucker defekt")` | `{ id: 7, title: 'Drucker defekt' }` |
| Die Klasse gibt es auch zur Laufzeit | Das Interface gibt es nur beim Schreiben |
| Ein Java-`interface` ist ein Vertrag mit Methoden, den Klassen erfüllen | Ein TypeScript-`interface` beschreibt die Form von Daten |

Klassen gibt es in TypeScript auch. Du brauchst sie, wenn ein Objekt eigenes Verhalten und einen eigenen Zustand hat. Das kommt in AB 03.

:::info Warum ist `createdAt` ein Text und kein `Date`?
Einen Datentyp für Datum und Uhrzeit gibt es: `Date`. Er ist in JavaScript eingebaut, du erzeugst ihn mit `new Date('2026-11-02')`. Ein reines Datum wie `LocalDate` in Java kennt JavaScript aber nicht, ein `Date` ist immer ein Zeitpunkt mit Uhrzeit.

Der wichtigere Grund: **JSON hat keinen Datentyp für Datum.** Ein Datum kommt vom Server als Text an, zum Beispiel `"2026-11-02"`, und `response.json()` macht daraus kein `Date`. Würdest du `createdAt: Date` schreiben, behauptest du etwas, das zur Laufzeit nicht stimmt: Der Compiler glaubt dir, und `ticket.createdAt.getFullYear()` stürzt ab, weil dort ein Text liegt. Genau dieses Problem lernst du in AB 03 kennen („der Compiler glaubt dir“).

Darum ist das Datum hier ein Text im Format `'JJJJ-MM-TT'` (ISO 8601, zum Beispiel `'2026-11-02'`). Dieses Format sortiert sich als Text schon in Datumsreihenfolge. Brauchst du später ein `Date`, wandelst du den Text an der Stelle um: `new Date(ticket.createdAt)`.
:::

### Aufgabe 5 – Drei Funktionen schreiben

*Etwa 30 Minuten.*

Jetzt kommen die ersten Funktionen. Für jede gibt es Tests, die du als Arbeitsliste nutzt: Lies zuerst die Namen der Tests in der Ausgabe von `npm run test:ab01`, dann schreibst du die Funktion.

#### A3: `describeTicket`

Die Funktion bekommt ein Ticket und **gibt einen Text zurück**, eine Zeile für die Anzeige. Sie schreibt nichts auf die Konsole: Sie liefert den Text mit `return` an den Aufrufer. Was der damit macht, ist seine Sache. Im Moment sind das die Tests, später die Oberfläche.

| Ticket | Ergebnis |
|---|---|
| Nummer 7, Titel `Drucker defekt`, Status `offen` | `#7 Drucker defekt [offen]` |

Diese Funktion bekommst du als Vorlage zum Übernehmen. Die Erklärung dazu folgt direkt darunter.

<Task id="ts-ab01-a5-describe">Öffne `src/ticket.ts`. Ersetze in `describeTicket` **nur** die Zeile `throw new Error('TODO A3: describeTicket');` durch die Zeile mit `return`. Die Zeile mit `export function` bleibt stehen. Die Funktion sieht danach so aus:</Task>

```ts title="src/ticket.ts"
export function describeTicket(ticket: Ticket): string {
  return `#${ticket.id} ${ticket.title} [${ticket.status}]`;
}
```

<Task id="ts-ab01-a5-describe-test">Starte `npm run test:ab01`. Die Tests `A3 describeTicket` sind jetzt grün.</Task>

**So funktioniert die Funktion:**

- `describeTicket(ticket: Ticket): string` ist der Kopf der Funktion. Anders als in Java steht der Typ **hinter** dem Namen: `ticket: Ticket` heißt „Parameter `ticket` vom Typ `Ticket`“, und `: string` hinter den Klammern ist der Typ des Ergebnisses.
- `return` gibt den Text an den Aufrufer zurück. Die `throw`-Zeile davor war nur der Platzhalter: Sie bricht das Programm mit einem Fehler ab, deshalb waren die Tests rot.
- Der Text steht zwischen **Backticks** und heißt **Template-String**. Mit `${…}` setzt du an dieser Stelle einen Wert ein, hier den Wert eines Feldes: `${ticket.id}` ist die Nummer, `${ticket.title}` der Titel. Alles andere, das `#`, die Leerzeichen und die eckigen Klammern, bleibt als Text stehen. Aus dem Ticket von oben wird `#7 Drucker defekt [offen]`.
- In Java hättest du die Teile mit `+` verbunden: `"#" + ticket.getId() + " " + ticket.getTitle() + …`. Das geht in TypeScript auch. Der Template-String ist lesbarer. Beachte außerdem: Auf die Felder greifst du direkt zu (`ticket.id`), es gibt keine Getter.
- Den Backtick tippst du auf der deutschen Tastatur mit **Umschalt + ´** (die Taste rechts neben dem ß) und danach der **Leertaste**. Die Taste wartet sonst auf einen Buchstaben, den sie mit dem Akzent versehen soll, und die Leertaste setzt den Backtick allein.

Mehr zu Template-Strings steht im Infoblatt [Typen](/infoblaetter/typen).

<Task id="ts-ab01-a5-describe-typo">Probiere, was der Typ dir hier bringt: Ändere `${ticket.status}` kurz in `${ticket.statu}`. WebStorm unterstreicht den Fehler sofort rot, und `npm run check` meldet, dass es das Feld nicht gibt. Mach die Änderung wieder rückgängig.</Task>

#### A4: `isUrgent`

Ein Ticket ist **dringend**, wenn es die Priorität 1 hat **und** noch nicht erledigt ist.

Zum Vergleichen schreibst du in TypeScript `===` (gleich) und `!==` (ungleich), nicht `==` und `!=` wie in Java. Das einfache `==` wandelt die Werte vorher um (`'4' == 4` ist in JavaScript wahr) und wird deshalb nicht benutzt. „Und“ schreibst du wie in Java `&&`.

#### A5: `assigneeName`

Die Funktion liefert den Namen der bearbeitenden Person als Text. Gibt es keine, ist das Ergebnis der Text `nicht zugewiesen`.

| Ticket | Ergebnis |
|---|---|
| `assignee` ist `'Mara Voss'` | `Mara Voss` |
| Das Feld `assignee` fehlt | `nicht zugewiesen` |

Das Feld `assignee` ist optional (Aufgabe 3). Fehlt es, ist sein Wert `undefined`. Auch diese Funktion bekommst du als Vorlage zum Übernehmen, die Erklärung folgt direkt darunter.

<Task id="ts-ab01-a5-assignee">Ersetze in `assigneeName` **nur** die Zeile `throw new Error('TODO A5: assigneeName');` durch die Zeile mit `return`. Die Zeile mit `export function` bleibt stehen. Die Funktion sieht danach so aus:</Task>

```ts title="src/ticket.ts"
export function assigneeName(ticket: Ticket): string {
  return ticket.assignee ?? 'nicht zugewiesen';
}
```

<Task id="ts-ab01-a5-assignee-test">Starte `npm run test:ab01`. Die drei Tests `A5 assigneeName` sind jetzt grün.</Task>

**Was bedeutet `??`?**

`??` heißt: „Nimm den linken Wert. Fehlt er (`undefined` oder `null`), nimm den rechten.“ In Java würdest du schreiben: `ticket.getAssignee() != null ? ticket.getAssignee() : "nicht zugewiesen"`. `??` ist die Kurzform dafür.

| Ausdruck | Ergebnis | Warum |
|---|---|---|
| `undefined ?? 'nicht zugewiesen'` | `'nicht zugewiesen'` | links fehlt der Wert |
| `null ?? 'nicht zugewiesen'` | `'nicht zugewiesen'` | `null` heißt auch „kein Wert“ |
| `'Mara Voss' ?? 'nicht zugewiesen'` | `'Mara Voss'` | links steht ein Wert |
| `'' ?? 'nicht zugewiesen'` | `''` | ein leerer Text ist ein Wert und bleibt |

Der Typ von `ticket.assignee` ist `string | undefined`, gesprochen „Text **oder** undefined“. Hinter dem `??` steht ein Text. Damit ist das Ergebnis der ganzen Zeile immer ein `string`, und genau das verlangt der Rückgabetyp der Funktion.

<Task id="ts-ab01-a5-assignee-check">Probiere, was der Compiler dazu sagt: Lösche kurz ` ?? 'nicht zugewiesen'`. WebStorm unterstreicht die Zeile rot, und auch `npm run check` meldet `Type 'string | undefined' is not assignable to type 'string'`. Der Compiler lässt nicht zu, dass du den Fall „kein Bearbeiter“ vergisst. Setze den Teil danach wieder ein.</Task>

<details>
<summary>Zusatz: Warum nicht `||`?</summary>

In Java kennst du `||` als „oder“ für Wahrheitswerte. In JavaScript und TypeScript wählt `||` außerdem den rechten Wert, wenn der linke „unecht“ ist. Das ist mehr als „fehlt“: Unecht sind der leere Text `''`, die Zahl `0`, `false`, `undefined` und `null`. Du wirst `||` in fremdem Code oft sehen.

Probiere es aus: Ersetze `??` kurz durch `||` und starte `npm run test:ab01`. Ein Test wird rot, nämlich `ein leerer Name ist ein Name und wird nicht ersetzt`. Er prüft ein Ticket mit dem leeren Namen `''`. `||` ersetzt ihn durch `nicht zugewiesen`, `??` lässt ihn stehen. Setze danach wieder `??` ein.

Für optionale Felder ist meistens `??` richtig, weil es nur ersetzt, wenn wirklich etwas fehlt.

</details>

## Zusammenfassung

:::tip Das hast du gelernt
- Der **Compiler** (`npm run check`) prüft Typen, die **Tests** (`npm run test:ab01`) prüfen Verhalten. Beides ist nötig.
- **Typen gibt es nur beim Schreiben:** Das Programm läuft auch mit Typfehlern, weil die Typen beim Kompilieren verschwinden.
- Ein **Interface** beschreibt die Form von Daten. Optionale Felder tragen ein `?`, unveränderliche das Wort `readonly`.
- Ein **Union-Typ** wie `'offen' | 'in Arbeit' | 'erledigt'` erlaubt nur die genannten Werte und gibt dem Editor Vorschläge.
- Ein **Template-String** setzt Werte mit `${…}` in einen Text ein.
- `??` ersetzt nur `undefined` und `null`, ein leerer Text bleibt ein Wert. Für optionale Felder ist meistens `??` richtig.
:::

## Selbstkontrolle

1. Was bedeutet das Fragezeichen in `assignee?: string`, und was ist der Wert, wenn das Feld fehlt?
2. Warum läuft das Programm in Aufgabe 2 trotz der Typfehler?
3. Was ist der Unterschied zwischen `status: string` und `status: Status` (mit dem Union-Typ)?
4. Was liefert `undefined ?? 'nicht zugewiesen'`, und was liefert `'' ?? 'nicht zugewiesen'`?
5. Ein Kollege schreibt `status: any`. Was geht dadurch verloren?
6. Wozu dient `readonly` bei `id`? Wann meldet der Compiler dann einen Fehler?

<details>
<summary>Antworten</summary>

1. Das Feld darf fehlen. Fehlt es, ist sein Wert `undefined`. Der Compiler erinnert dich daran, das beim Lesen zu behandeln.
2. Der Compiler entfernt die Typen beim Übersetzen. Was ausgeführt wird, ist reines JavaScript, und das kennt keine Typen. Typfehler sind Warnungen des Compilers, keine Laufzeitfehler.
3. `string` erlaubt jeden Text, auch `'wartet'` und Tippfehler. Der Union-Typ erlaubt nur die drei genannten Werte. Der Compiler meldet alles andere, und der Editor schlägt die gültigen Werte vor.
4. `undefined ?? 'nicht zugewiesen'` liefert `'nicht zugewiesen'`, weil links der Wert fehlt. `'' ?? 'nicht zugewiesen'` liefert `''`, weil `??` nur bei `undefined` und `null` ersetzt und ein leerer Text ein Wert ist.
5. Mit `any` prüft der Compiler das Feld nicht mehr. Falsche Werte und Tippfehler fallen nicht auf, und der Editor kann keine Vorschläge machen. `any` schaltet die Prüfung für diese Stelle aus.
6. `readonly` schützt die Nummer davor, nachträglich geändert zu werden. Der Compiler meldet einen Fehler, sobald jemand zum Beispiel `ticket.id = 5` schreibt.

</details>
