# AB 03 – Speicher und Daten laden

*Dauer: etwa eine Doppelstunde.*

## Die Situation

> Die Auswertungen der Support-Tickets funktionieren. Bisher lagen die Tickets in einer Excel-Datei auf dem Netzlaufwerk: Wer eine Änderung sehen wollte, musste die Datei neu öffnen. Künftig kommen die Tickets von einem **Server**, und die Oberfläche soll **sofort** aktuell sein, wenn sich ein Ticket ändert: in der Liste, im Zähler, überall.
>
> Dein Auftrag: Baue einen **Speicher**, der die Tickets hält, Änderungen meldet und Tickets aus dem Netz laden kann.

## Lernziele

Nach Bearbeitung dieses Arbeitsblatts kannst du:

- eine **Klasse** mit Konstruktor-Attributen und privatem Zustand schreiben
- erklären, warum ein Speicher **neue Listen** statt Änderungen an der alten braucht
- **Änderungen melden**, indem du Funktionen anmeldest und wieder abmeldest (Beobachter-Muster)
- Daten mit `async` und `await` laden und Fehler abfangen
- das Ergebnis mit einem **`Result`-Typ** darstellen, sodass der Compiler die Prüfung erzwingt

Der Compiler hat `push` verboten, und das ist richtig so: **Eine Liste, die der Speicher einmal herausgegeben hat, ändert er nie mehr.** Warum, zeigt ein Beispiel ohne Speicher. Es geht um dasselbe wie in Java: Zwei Namen können auf **dieselbe** Liste zeigen.

```ts
const list = [ticketA, ticketB];   // der Speicher hält diese Liste
const onScreen = list;             // all() gibt sie heraus, die Anzeige hält jetzt dieselbe Liste

list.push(ticketC);                // der Speicher hängt ein Ticket an: er verändert die Liste

onScreen.length;                   // 3: die Anzeige hat jetzt drei Tickets, ohne dass ihr jemand etwas gesagt hat
onScreen === list;                 // true: es gibt keinen Unterschied zwischen vorher und nachher
```

Daraus folgen zwei Probleme:

1. **Heimliche Änderung.** Jeder, der die Liste bekommen hat (die Ticketliste, der Zähler, die Statistik der Teamleiterin), sieht sie sich unter den Händen ändern. Der Zähler hat vielleicht schon „2 Tickets“ ausgerechnet, die Liste zeigt jetzt drei. Das ist ein Fehler, den niemand meldet.
2. **Keine Änderung erkennbar.** Eine Anzeige kann nur fragen: „Ist das noch dieselbe Liste wie vorhin?“ Wurde die Liste selbst verändert, lautet die Antwort immer „ja“, und die Anzeige bemerkt nichts. Genau das brauchst du in Aufgabe 4: Der Speicher meldet jede Änderung, und die Anzeige erkennt an der **neuen** Liste, dass sie neu zeichnen muss. Das gilt später auch in Angular, wenn du dort mit Signals arbeitest.

Baut der Speicher stattdessen eine **neue** Liste, bleiben beide Probleme aus:

```ts
const next = [...list, ticketC];   // neue Liste mit drei Tickets

onScreen.length;                   // 2: die Liste auf dem Bildschirm ist unverändert
onScreen === next;                 // false: die Anzeige kann den Unterschied erkennen
```

Deshalb entsteht bei jeder Änderung eine **neue** Liste, und das Attribut des Speichers verweist danach auf sie. Das ist dasselbe Prinzip wie bei `withStatus` in AB 02.

### Aufgabe 4 – Änderungen melden

*Etwa 20 Minuten.*

Der Speicher soll Änderungen melden. Dafür baust du ihn in vier kleinen Schritten um. Zu jedem Schritt gibt es Code zum Abtippen und darunter die Erklärung.

#### Schritt 1: Die Menge der Zuhörer

Der Speicher muss sich merken, **wer** informiert werden will. Das sind **Funktionen**, die er später aufruft.

Neu ist dabei: In TypeScript ist eine Funktion ein Wert wie eine Zahl oder ein Text. Du kannst sie in einer Variablen ablegen oder in eine Liste legen, und wer sie hat, kann sie später aufrufen. Das kennst du schon von `filter`, dem du eine Funktion übergeben hast. Ein Beispiel mit etwas anderem:

```ts
const greetEnglish = () => console.log('Hello');
const greetGerman = () => console.log('Hallo');

const greetings = [greetEnglish, greetGerman];   // zwei Funktionen in einer Liste

for (const greet of greetings) {
  greet();   // ruft jede gespeicherte Funktion auf: erst Hello, dann Hallo
}
```

Der Speicher legt seine Funktionen in einer **Menge** (`Set`) ab statt in einer Liste:

```ts
private readonly listeners = new Set<Listener>();
```

- `Set<Listener>` ist eine Menge von Funktionen vom Typ `Listener`. Der Typ steht schon in der Datei: eine Funktion, die die neue Liste bekommt und nichts zurückgibt.
- Ein `Set` enthält jedes Element nur einmal. Mit `add` kommt etwas hinein, mit `delete` geht es wieder heraus, und mit `for (const x of set)` gehst du alle durch.
- `readonly` steht hier, weil die Menge selbst nie ersetzt wird, nur ihr **Inhalt** ändert sich. Bei `tickets` war es anders: Dort wird die Liste bei jeder Änderung durch eine neue ersetzt.

<Task id="ts-ab03-a4-field">Schreibe die Zeile ab und setze sie an den Anfang der Klasse. `npm run check` meldet nichts Neues.</Task>

#### Schritt 2: Alle benachrichtigen

```ts
private notify(): void {
  for (const listener of this.listeners) {
    listener(this.tickets);
  }
}
```

- `for (const listener of this.listeners)` geht alle angemeldeten Funktionen durch.
- `listener(this.tickets)` **ruft** die Funktion auf und gibt ihr die aktuelle Liste mit. So erfährt jeder Zuhörer, wie die Liste jetzt aussieht.
- `private` heißt: Nur der Speicher selbst ruft `notify` auf. Von außen soll niemand eine Meldung auslösen.

#### Schritt 3: Anmelden und wieder abmelden

`onChange` macht zwei Dinge: Es merkt sich die Funktion, und es liefert als Ergebnis **eine Funktion zum Abmelden**. Eine Funktion, die eine Funktion zurückgibt, ist neu. Hier ein Beispiel mit etwas anderem:

```ts
function makeGreeter(greeting: string): () => string {
  return () => `${greeting}, Welt!`;
}

const hello = makeGreeter('Hallo');
hello();   // 'Hallo, Welt!'
```

Der Rückgabetyp `() => string` heißt: eine Funktion ohne Parameter, die einen Text liefert. Die zurückgegebene Funktion „erinnert sich“ an `greeting`, auch nachdem `makeGreeter` längst beendet ist. Man nennt das eine **Closure**. Damit sieht `onChange` so aus:

```ts
onChange(listener: Listener): () => void {
  this.listeners.add(listener);
  return () => {
    this.listeners.delete(listener);
  };
}
```

- `this.listeners.add(listener)` merkt sich die Funktion des Zuhörers.
- `return () => { … }` gibt eine **neue Funktion** zurück. Sie erinnert sich an `listener`, genau wie `hello` an `greeting`.
- Wer sich abmelden will, ruft diese Funktion auf: `const unsubscribe = store.onChange(…);` und später `unsubscribe();`. Sie entfernt den Zuhörer mit `delete` wieder aus der Menge.
- `() => void` im Rückgabetyp heißt: eine Funktion ohne Parameter, die nichts zurückgibt.

<Task id="ts-ab03-a4-onchange">Schreibe die Methode `onChange` ab.</Task>

#### Schritt 4: Beim Ändern melden

Bis jetzt meldet der Speicher noch nichts. Jede Methode, die die Liste ändert, ruft **danach** `notify()` auf:

```ts
add(ticket: Ticket): void {
  this.tickets = [...this.tickets, ticket];
  this.notify();
}

setStatus(id: number, status: Status): void {
  if (!this.tickets.some((ticket) => ticket.id === id)) {
    return;
  }
  this.tickets = withStatus(this.tickets, id, status);
  this.notify();
}

replaceAll(tickets: readonly Ticket[]): void {
  this.tickets = [...tickets];
  this.notify();
}
```

- `notify()` steht **nach** der Änderung. Die Zuhörer sollen die neue Liste sehen, nicht die alte.
- In `setStatus` steht es hinter dem `return`: Gibt es die Nummer nicht, hat sich nichts geändert, also gibt es nichts zu melden.

:::info Das Beobachter-Muster
Du hast gerade ein Muster gebaut, das in der Programmierung überall vorkommt: Ein Objekt (hier der Speicher) **meldet Änderungen**, und andere Objekte **melden sich an**, um sie zu erfahren. Wer fertig ist, meldet sich wieder ab.

In Angular löst das ein fertiger Baustein. Im nächsten Tutorial lernst du **Signals** kennen, mit denen die Oberfläche von selbst aktuell bleibt. `HttpClient` und viele andere Teile von Angular liefern **Observables**, die ähnlich funktionieren wie dein `onChange`: Man meldet sich an (`subscribe`) und bekommt einen Weg, sich abzumelden (`unsubscribe`). Ein Unterschied: Ein Observable startet seine Arbeit erst, wenn sich jemand anmeldet.
:::

### Aufgabe 5 – Daten laden

*Etwa 20 Minuten.*

Bisher kommen die Tickets aus dem Programm selbst. Echte Daten liegen auf einem Server, und dorthin muss man eine Anfrage schicken. Das dauert, und währenddessen darf das Programm nicht stehen bleiben. Dafür gibt es `async` und `await`.

**C3** `loadTickets(url)` ruft die Adresse ab und liefert die Tickets. Bei einer Fehlerantwort wirft sie einen Fehler mit dem Text `HTTP <status>`.

<Task id="ts-ab03-a5-predict">Vorhersage: Du rufst mit `fetch` eine Adresse ab, die es nicht gibt. Der Server antwortet mit **404**. Löst `fetch` dann einen Fehler aus? Notiere deine Vermutung.</Task>

<details>
<summary>Auflösung</summary>

Nein. `fetch` meldet einen Fehler nur, wenn das **Netz** scheitert (kein Internet, Adresse unbekannt). Eine Antwort mit 404 oder 500 ist für `fetch` eine ganz normale Antwort. Ob sie gut war, musst du selbst prüfen, mit `response.ok`.

</details>

So sieht die Funktion `loadTickets` aus. Sie ist neu, deshalb steht sie hier vollständig:

```ts title="src/ticket-store.ts"
export async function loadTickets(url: string): Promise<Ticket[]> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return (await response.json()) as Ticket[];
}
```

- `async` kennzeichnet eine Funktion, die auf etwas wartet. Ihr Ergebnis ist immer ein **`Promise`**, eine Zusage auf einen Wert, der später da ist. `Promise<Ticket[]>` heißt: später liegt hier eine Liste von Tickets.
- `await fetch(url)` ruft die Adresse ab und **wartet** auf die Antwort: Nur **diese Funktion** pausiert an dieser Stelle und macht danach weiter. Das übrige Programm (zum Beispiel die Oberfläche) läuft in der Zwischenzeit weiter. In Java wäre es anders: `future.get()` blockiert den ganzen Thread. `await` darfst du in einer `async`-Funktion benutzen. Auf oberster Ebene einer Datei, wie in `explore/load.ts`, geht es auch ohne `async`.
- `response.ok` ist wahr, wenn der Server mit Erfolg geantwortet hat. Sonst wirft die Funktion einen Fehler mit dem Text `HTTP 404` (oder die jeweilige Nummer).
- `await response.json()` liest den Inhalt der Antwort als Daten, und `as Ticket[]` sagt dem Compiler, welche Form sie haben.

<Task id="ts-ab03-a5-load">Übernimm die Funktion in `src/ticket-store.ts`. Sie ersetzt den Platzhalter `loadTickets`.</Task>

<Task id="ts-ab03-a5-test1">Starte `npm run test:ab03`. Die zwei Tests `loadTickets` in der Gruppe `C3` werden grün. Sie benutzen ein **vorgegebenes** `fetch` und brauchen kein Netz.</Task>

:::warning Der Compiler glaubt dir
Mit `as Ticket[]` **behauptest** du, dass die Daten die Form von Tickets haben. Der Compiler prüft das nicht, und zur Laufzeit gibt es keine Typen mehr. Liefert der Server ein Ticket ohne `title`, merkst du es erst, wenn dein Code darauf zugreift. Typen am Rand der Anwendung sind Behauptungen.

Jetzt der Blick auf die Fehlerfälle. Eine Funktion, die wirft, überlässt es dem Aufrufer, ob er den Fehler behandelt. Der Compiler erzwingt es nicht. Besser: Die Funktion liefert ein Ergebnis, das **entweder** die Daten **oder** den Fehler enthält und das du **nicht ignorieren** kannst.

<Task id="ts-ab03-a5-type">Ersetze `export type Result<T> = any;` durch einen **Union-Typ**:</Task>

```ts
export type Result<T> = { ok: true; data: T } | { ok: false; error: string };
```

Lies ihn so: Ein `Result<T>` ist **entweder** ein Objekt mit `ok: true` und den Daten **oder** ein Objekt mit `ok: false` und einem Fehlertext.

<Task id="ts-ab03-a5-check">Starte `npm run check`. Die letzte offene Meldung (die mit `C4`) ist verschwunden. Der Compiler ist jetzt vollständig zufrieden. Lies den Kommentar über der Zeile in `src/types.check.ts`: Was verlangt der Compiler jetzt von jedem, der ein `Result` benutzt?</Task>

<details>
<summary>Auflösung</summary>

Wer ein `Result` benutzt, **muss** zuerst prüfen, ob `ok` wahr ist. Erst dann weiß der Compiler, ob es `data` oder `error` gibt. Greift man ohne Prüfung auf `data` zu, meldet er `Property 'data' does not exist on type 'Result<Ticket[]>'`.

</details>

**C4** `loadTicketsSafe(url)` ruft `loadTickets` auf, wirft aber **nie**, sondern liefert ein `Result`.

Eine Neuerung gibt es noch beim Fehlertext. Der Fehler im `catch` hat den Typ `unknown`, denn in JavaScript kann man alles werfen, nicht nur Fehlerobjekte. Prüfe, ob es ein Fehlerobjekt ist, bevor du den Text benutzt. Ein Beispiel mit etwas anderem:

```ts
try {
  riskyCall();
} catch (error: unknown) {
  const text = error instanceof Error ? error.message : String(error);
}
```

`error instanceof Error` kennst du aus Java: Es prüft, ob der Wert ein Fehlerobjekt ist. Dann steht sein Text in `error.message`. Sonst macht `String(error)` aus jedem beliebigen Wert einen Text.

<Task id="ts-ab03-a5-safe">Schreibe `loadTicketsSafe` mit `try` und `catch`. Im `try` liefert die Funktion `{ ok: true, data: … }`, im `catch` `{ ok: false, error: … }`. `loadTickets(url)` liefert ein `Promise`, deshalb brauchst du vor dem Aufruf `await`. Den Text im `catch` holst du wie im Beispiel oben.</Task>

:::tip Eine Meldung, die du jetzt kennen solltest
`Type 'Promise<Ticket[]>' is missing the following properties from type 'Ticket[]' …` heißt fast immer: Du hast `await` vergessen. Der Compiler hat ein `Promise` bekommen, wo er die Liste selbst erwartet.
:::

<details>
<summary>Lösung: loadTicketsSafe</summary>

```ts title="src/ticket-store.ts"
export async function loadTicketsSafe(url: string): Promise<Result<Ticket[]>> {
  try {
    return { ok: true, data: await loadTickets(url) };
  } catch (error: unknown) {
```

## Zusammenfassung

:::tip Das hast du gelernt
- Eine **Klasse** hält Zustand und Verhalten zusammen. Ein Konstruktor-Parameter mit `private` ist gleichzeitig ein Feld.
- Ein Speicher gibt bei jeder Änderung eine **neue Liste** aus. Wer eine alte Liste hat, behält sie unverändert.
- **Beobachter-Muster:** Der Speicher merkt sich angemeldete Funktionen und ruft sie bei jeder Änderung auf. `onChange` liefert eine Funktion zum Abmelden.
- **`async` und `await`** laden Daten, ohne das übrige Programm anzuhalten. Eine `async`-Funktion liefert ein `Promise`.
- **`fetch` wirft nicht bei 404:** Die Antwort musst du mit `response.ok` selbst prüfen.
- Ein **`Result<T>`** stellt Erfolg oder Fehler als Union-Typ dar. Der Compiler zwingt jeden, zuerst `ok` zu prüfen.
- Typen am Rand der Anwendung (JSON vom Server) sind **Behauptungen**, die niemand prüft.
:::

## Selbstkontrolle

1. Was bewirkt das Wort `private` vor einem Konstruktor-Parameter?
2. Warum ersetzt `add` die Liste, statt mit `push` ein Element anzuhängen?
3. Wozu liefert `onChange` eine Funktion zurück? Was passiert, wenn man sie aufruft?
4. Was macht `await`, und was liefert eine Funktion, die mit `async` gekennzeichnet ist?
5. Der Server antwortet mit 404. Warum wirft `fetch` trotzdem keinen Fehler, und was musst du tun?
6. Was behauptest du mit `as Ticket[]`, und was prüft der Compiler dabei nicht?

<details>
<summary>Antworten</summary>

1. Der Parameter wird gleichzeitig zu einem **privaten Feld** der Klasse, und der übergebene Wert wird ihm zugewiesen. Dafür braucht der Konstruktor keinen eigenen Inhalt.
2. `push` würde die Liste verändern, die ein anderer schon in der Hand hält. Mit einer neuen Liste bleibt die alte unverändert, und jeder, der gemeldet bekommt, erhält die neue.
3. Die zurückgegebene Funktion **meldet den Listener wieder ab**. Nach dem Aufruf bekommt er keine Änderungen mehr. So räumt man auf, wenn eine Anzeige nicht mehr gebraucht wird.
4. `await` wartet auf ein `Promise` und liefert seinen Wert, ohne das Programm insgesamt anzuhalten. Es ist nur in einer `async`-Funktion erlaubt. Eine `async`-Funktion liefert selbst immer ein `Promise`.
5. Für `fetch` ist eine Antwort mit Status 404 eine ganz normale Antwort. Ein Fehler tritt nur ein, wenn das Netz selbst scheitert. Du musst `response.ok` (oder `response.status`) prüfen und selbst einen Fehler werfen.
6. Du behauptest, dass die Daten aus dem Netz die Form eines `Ticket`-Arrays haben. Der Compiler glaubt dir. Er prüft **nicht**, ob die Daten das wirklich tun, und zur Laufzeit gibt es keine Typen, die es prüfen könnten.

</details>
